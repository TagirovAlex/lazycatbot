# Архитектура ChessBot 2.0 NNUE

Документ описывает устройство движка по состоянию исходников на 2026-11-24. Он
дополняет [README.md](../README.md) и [ALGORITHMS.md](ALGORITHMS.md), но не заменяет
чтение кода.

## 1. Назначение и границы

ChessBot 2.0 NNUE — компактный UCI-движок на C++20. У него нет внешних зависимостей
для шахматной логики: битборды, генерация ходов, поиск, оценка, TT и UCI реализованы
внутри проекта. Внешние инструменты (`python-chess`, Stockfish 19) используются только
в тестовых/разметочных скриптах и не входят в исполняемый движок.

Ключевое архитектурное решение: **поиск многопоточный через Lazy SMP**. Основной
поток (`search_`) и helpers делят TT и `SharedSearchState` (stop/nodes); история,
killers и PV у каждого потока свои. `Threads` = 1…16. Syzygy probe вынесен в
`src/syzygy.cpp` (Fathom): WDL можно вызывать из всех потоков, root DTZ — только
из главного. MultiPV/Ponder в эту сборку не входят — они сохранены отдельно в
`experiments/multipv_build`.

## 2. Общая схема

```text
                 stdin/stdout (UCI)
                        |
                 +------v-------+
                 |  UciEngine   |  src/uci.cpp
                 +------+-------+
                        |
        +---------------+----------------+
        |               |                |
  +-----v-----+   +-----v------+   +-----v------+
  | Position  |   |    TT      |   |  Search    |
  | position  |   | search.cpp |   | search.cpp |
  +-----+-----+   +-----+------+   +-----+------+
        |               |                |
        |               |        +-------v--------+
        |               |        |   evaluate()   |
        |               |        |    eval.cpp    |
        |               |        +-------+--------+
        |               |                |
        |               |      +---------v----------+
        |               |      | classicalEvaluate  |
        |               |      | + NNUE::correction  |
        |               |      +--------------------+
        |               |
        +-------> generateMoves / makeMove / unmakeMove
                        |
                  perft / SEE / draw detection
```

Поток данных при поиске:

1. UCI-слой разбирает `position` и создаёт `Position`.
2. `go` формирует `SearchLimits`, сбрасывает `stopFlag` и запускает `Search::run`
   в отдельном потоке.
3. `Search::run` строит список легальных корневых ходов, затем выполняет итеративное
   углубление: `searchRoot` → `negamax` → `quiescence`.
4. В листьях вызывается `evaluate`, которая считает классическую оценку и, если
   включено, добавляет/смешивает выход сети.
5. `info`-строки печатаются после завершённой глубины; по завершении печатается
   `bestmove`.
6. `stop`/`quit` выставляют атомарный флаг; поиск проверяет его каждые 1024 узла и
   между глубинами.

## 4. Инициализация

В `main()` (и в `trainer.cpp`) вызывается `chess::initAll()`:

```cpp
void initAll() {
    Bitboards::init();   // leap attacks, линии, magic-таблицы
    Zobrist::init();     // psq[12][64], castling[16], epFile[8], side
    initEvaluation();    // passedMask, NNUE::init()
}
```

`Bitboards::init()`:

- строит атаки коня, короля и пешек для всех 64 полей;
- строит таблицы `between[64][64]` и `line[64][64]`;
- генерирует magic-числа для слонов и ладей.

Magic-числа не зашиты в исходник: они подбираются при каждом старте процесса
детерминированным `std::mt19937_64` с фиксированными seed-константами. Таблицы
`rookTable[64][4096]` и `bishopTable[64][1024]` лежат в BSS (около 2,6 МБ) и
заполняются при инициализации. Это упрощает код и делает поведение воспроизводимым,
но добавляет небольшую задержку на старте.

`initEvaluation()` строит маску проходных пешек и вызывает `NNUE::init()`. В текущей
сборке `NNUE::init()` пустой: веса уже находятся в массивах, сгенерированных
тренером.

## 5. Представление позиции

`Position` хранит:

| Поле | Назначение |
|---|---|
| `byType[6]` | битборды пешек, коней, слонов, ладей, ферзей, королей |
| `byColor[2]` | битборды белых и чёрных |
| `occ` | объединённый occupancy |
| `board[64]` | «почтовый» массив фигур (`W_PAWN`…`B_KING`, `NO_PIECE`) |
| `side` | сторона хода |
| `castling` | битовая маска прав рокировки (`WHITE_OO`, `WHITE_OOO`, `BLACK_OO`, `BLACK_OOO`) |
| `ep` | поле взятия на проходе или `-1` |
| `halfMove`, `fullMove` | счётчики для правила 50 ходов и FEN |
| `key` | текущий Zobrist-ключ |
| `kingSq[2]` | позиции королей |
| `histPly`, `keyHist[]`, `undoStack[]` | история для отката, повторений и Zobrist |
| `isNullHist_[]` | пометки null-move, чтобы повторения не считали их реальными ходами |

`MAX_HIST = 4096`, `MAX_PLY = 128`. История хранится прямо в объекте `Position`,
поэтому копирование позиции дорогое; поиск работает по ссылке (`Position&`), а не по
значению.

### FEN

`setFen`:

- разбирает доску, сторону хода, права рокировки, en passant, счётчики;
- проверяет, что в каждой строке ровно 8 полей и что оба короля присутствуют;
- отклоняет больше 32 фигур, больше 8 пешек на сторону, двух королей одного цвета,
  соседних королей, неверную сторону хода и неизвестные символы рокировки;
- нормализует права рокировки, если король/ладья уже не на месте;
- принимает en passant только если это реальное взятие (есть пешка и поле пустое);
- ограничивает счётчики (`halfMove <= 1000`, `fullMove <= 1'000'000`);
- отклоняет позицию, в которой только что ходившая сторона оставила своего короля
  под шахом;
- вычисляет `key` с нуля;
- сбрасывает `histPly`, `keyHist[0]` и `isNullHist_[0]`.

`fen()` собирает строку обратно; `ascii()` печатает доску для команды `d`.
При ошибке `setFen` возвращает `false`, но позиция остаётся очищенной (без королей).
`UciEngine` проверяет результат: сбрасывает позицию в startpos и печатает
`info string invalid FEN, using startpos`; `go` дополнительно страхует случай
`kingSq == -1`. Прямые вызовы `setFen` вне UCI обязаны проверять `false` сами.

### makeMove / unmakeMove

`makeMove` — основной «рабочий» метод. Порядок:

1. Сохранить `Undo` (ключ, права, ep, счётчики, взятая фигура).
2. Убрать из ключа старые castling/ep-компоненты.
3. Обработать взятие (включая en passant) и убрать фигуру.
4. Переместить фигуру, при превращении заменить её на нужный тип.
5. Переместить ладью при рокировке.
6. Обновить права рокировки (король/ладья).
7. Выставить новое поле ep только для двойного хода пешки.
8. Обновить halfmove/fullmove, сторону, ключ.
9. Проверить, не остался ли король ходящей стороны под шахом. Если да — откатить
   ход и вернуть `false`.

Перед изменениями `makeMove` проверяет `histPly`, корректность from/to и (для
en passant) наличие пешки на ожидаемом поле. `makeNullMove` возвращает `bool`:
если история заполнена, null-move не выполняется. Каждый null-move помечается в
`isNullHist_`, чтобы `isRepetition()` не принимал его за реальный ход.

Таким образом, `makeMove` одновременно является проверкой легальности. Это упрощает
код и гарантирует, что нелегальные ходы не попадут в поиск, но делает perft медленнее
«чистого» bulk-perft.

`unmakeMove` восстанавливает позицию из `Undo` и `keyHist`; для повышения надёжности
он не пересчитывает ключ, а берёт сохранённый.

### Ничьи

`isDraw()` возвращает true при:

- `halfMove >= 100` (правило 50 ходов);
- повторении позиции: `isRepetition()` сравнивает текущий ключ с ключами на 2, 4, …
  полуходов назад в пределах `halfMove`;
- недостаточном материале (`isInsufficientMaterial`): K vs K, K+одна лёгкая фигура,
  а также позиция без коней/пешек/ладей/ферзей, где все оставшиеся слоны стоят на
  полях одного цвета (включая KB vs KB и более экзотические случаи).

Это не полный анализ «мёртвых» позиций FIDE, а практический набор правил для поиска.
Например, KNN vs K не считается автоматической ничьей (мат там не форсирован, но
позиция не «мертва»). `isRepetition()` пропускает позиции, достигнутые null-move:
они помечены в `isNullHist_[]` и не должны создавать ложное повторение.

### En passant и хеш

`epHashable()` возвращает true, только если на поле `ep` действительно может пойти
пешка соперника. Если взятия на проходе нет, поле ep не попадает в Zobrist-ключ. Это
уменьшает число «лишних» различных ключей для позиций, отличающихся только
неактуальным ep-полем.

## 6. Кодирование хода и генерация

`Move` — 32-битное слово, но реально используются 19 бит:

| Биты | Содержимое |
|---|---|
| 0–5 | from |
| 6–11 | to |
| 12–14 | тип превращения (0 — нет, иначе KNIGHT…QUEEN) |
| 15–17 | тип хода: NORMAL, DOUBLE_PUSH, EN_PASSANT, CASTLE, PROMOTION |
| 18 | флаг взятия |

`MoveList` — фиксированный массив на 256 ходов; динамических аллокаций в генерации
нет.

`generateMovesImpl(list, capturesOnly)`:

- пешки: ходы вперёд, двойной ход со стартовой горизонтали, взятия, en passant,
  превращения (в том числе превращения-взятия);
- кони, слоны, ладьи, ферзи: атаки из magic-таблиц, пересечённые с `~own`;
- король: обычные ходы; рокировка проверяет пустые поля, наличие ладьи и что
  король не проходит через битые поля;
- `capturesOnly` используется в quiescence; при этом невзяточные превращения пешек
  всё равно включаются, потому что превращение меняет материал.

Псевдолегальные ходы проверяются в `makeMove`; на корне `Search::run` дополнительно
фильтрует список, оставляя только те ходы, после которых `makeMove` вернул true.

`SEE` реализован рекурсивно: `attackersTo` собирает всех атакующих на поле с учётом
текущего occupancy, затем выбирается наименее ценная фигура, occupancy обновляется,
и оценка возвращается как `targetValue - seeRec(...)`. Результат ограничен снизу
нулём; это стандартная упрощённая SEE, а не полный анализ всех x-ray-связок.

`perft` рекурсивно вызывает `generateMoves`/`makeMove`; на глубине 1 считает
легальные ходы. Он используется как основной тест корректности генератора.

## 7. Хеширование и транспозиционная таблица

### Zobrist

Массивы:

- `psq[12][64]` — фигура на поле;
- `castling[16]` — маска прав рокировки;
- `epFile[8]` — файл en passant (если `epHashable()`);
- `side` — xor при смене стороны.

Ключ обновляется инкрементально в `makeMove`/`unmakeMove`; `setFen` пересчитывает его
с нуля. 64-битный ключ используется для повторений и как источник индекса TT.

### TTEntry

```cpp
struct TTEntry {
    uint32_t key;    // 32-bit signature
    uint32_t move;   // Move::raw()
    int16_t score;
    int16_t eval;
    uint8_t depth;
    uint8_t bound;
    uint8_t gen;
    uint8_t pad;
};
static_assert(sizeof(TTEntry) == 16);
```

`TranspositionTable`:

- `resize(megabytes)` выделяет массив записей, округляя количество вниз до степени
  двойки; минимум 1024 записи;
- индекс — `key & mask_`;
- сигнатура — `uint32_t(key) ^ uint32_t(key >> 32)`;
- `probe` проверяет сигнатуру и `bound != BOUND_NONE`;
- `store` сначала решает, стоит ли заменять запись:
  - при совпадении сигнатуры запись сохраняется, если новая глубина более чем на 3
    меньше старой;
  - при другой сигнатуре в том же поколении запись сохраняется, если новая глубина
    меньше старой;
  - иначе запись заменяется;
- `newSearch()` инкрементирует 8-битное поколение (с переполнением);
- `hashfull()` смотрит первые 1000 записей и оценивает заполнение текущего поколения.

Одна запись на индекс, без кластеров и без bucket replacement. 32-битная сигнатура
означает ненулевой (хотя и небольшой) шанс коллизии. Для учебного движка этого
достаточно, но это заметно слабее TT топовых движков.

Матовые оценки хранятся с поправкой на ply (`scoreToTT`/`scoreFromTT`): при записи
`score + ply` для мата за нас и `score - ply` для мата против, при чтении — обратно.
Это позволяет корректно использовать одну и ту же позицию на разной глубине от корня.

## 8. Оценка

### Классическая часть

`classicalEvaluate` считает `mg` и `eg` в сантипешках, затем смешивает их по фазе:

```text
phase = sum(phaseInc[piece]) для непешных фигур
phaseInc: N/B = 1, R = 2, Q = 4
MaxPhase = 24
score = (mg * phase + eg * (MaxPhase - phase)) / MaxPhase
```

Порядок вычислений:

1. Материал + PST для каждой фигуры (белые — `sq`, чёрные — `sq ^ 56`).
2. Мобильность: количество полей, атакованных фигурой, кроме своих; веса
   N 4/3, B 3/4, R 2/3, Q 1/1 (mg/eg).
3. Пара слонов: +30 mg / +45 eg.
4. Пешки: сдвоенные, изолированные, проходные; защищённый проходник.
5. Ладьи: открытая/полуоткрытая линия, 7-я горизонталь.
6. Кони: форпост на относительной горизонтали 3–5, поддержанный пешкой и не
   атакованный вражеской пешкой.
7. Безопасность короля: пешечный щит (14/7/−10 за пешку впереди/двумя/ничего),
   открытая линия рядом с королём (−18), давление фигур на королевское кольцо
   (вес 2/3/5 для лёгких/ладьи/ферзя, умножается на 4).
8. Пространство: свои фигуры на центральных полях c–f (для белых относительные
   горизонтали 3–5, для чёрных 4–6), +2 mg за фигуру.
9. Mop-up при `phase <= 6` и перевесе материала > 300: приближение слабого короля
   к краю и к сильному королю.
10. Темп: +10 cp стороне хода.

Давление на королевское кольцо собирается с фигур обеих сторон, а итоговый
king-safety применяется после обхода фигур: иначе белые могли бы не учитывать
атакующие фигуры чёрных (и наоборот).

Оценка возвращается с точки зрения стороны хода: белые — как есть, чёрные — с
обратным знаком. Значение ограничивается `±(MATE_IN_MAX − 1)`.

### NNUE-часть

`evaluate`:

```cpp
int base = classicalEvaluate(pos);
if (NNUE::trained && NNUE::enabled && NNUE::weight > 0) {
    int net = NNUE::correction(pos);
    if (NNUE::direct)
        base = (net * weight + base * (100 - weight)) / 100;
    else
        base += net * weight / 100;
}
return clamp(base, -MATE_IN_MAX + 1, MATE_IN_MAX - 1);
```

`NNUE::correction`:

- строит 768-мерный разреженный вектор признаков (до 32 ненулевых);
- считает `h = B1 + Σ W1[feature]`, применяет ReLU;
- считает `out = B2 + Σ W2[j] * h[j]`;
- переводит выход из «пешек» в сантипешки: `round(out * 100)`;
- ограничивает результат ±1500 cp.

Признаки: для каждой фигуры `relColor` = 0, если цвет совпадает со стороной хода,
иначе 1; поле зеркалится по вертикали для чёрных; индекс
`(relColor * 6 + pieceType) * 64 + square`. Король участвует как обычная фигура, без
королевского бакета. Это важно: **это не HalfKP**, несмотря на комментарий
«HalfKP-like» в исходнике.

## 9. Поиск

### Итеративное углубление и aspiration

`Search::run`:

1. Инициализирует счётчики, время, историю.
2. Строит `rootMoves_` — только легальные ходы.
3. Для `depth = 1..maxDepth`:
   - с глубины 4 задаёт окно `[prevScore − 30, prevScore + 30]`;
   - вызывает `searchRoot`; при выходе за окно расширяет его (delta удваивается);
   - после завершённой глубины печатает `info`, сортирует корневые ходы по оценке;
   - останавливается по мату, мягкому/жёсткому лимиту времени или `stop`.
4. Печатает `bestmove` (или `0000`, если ходов нет).

Если поиск был прерван до завершения хотя бы одной глубины, используется
`rootFallback_` — первый легальный ход. Это защищает от `0000` в обычных позициях,
но означает, что при мгновенном `quit` после `go` можно получить слабый запасной ход.

### negamax

Порядок в `negamax`:

1. Защита от `ply >= MAX_PLY`.
2. Учёт узла и проверка времени каждые 1024 узла.
3. На не-корне: проверка ничьей, mate-distance pruning
   (`alpha = max(alpha, -MATE + ply)`, `beta = min(beta, MATE - ply - 1)`).
4. `depth <= 0` → `quiescence`.
5. Check extension: `if (inCheck) ++depth`.
6. TT probe; на не-PV узле при достаточной глубине — ранний возврат по bound.
7. Static eval (из TT или `evaluate`), `improving = staticEval > evalStack[ply-2]`.
8. Reverse futility pruning, razoring, null-move pruning. RFP/razoring дополнительно
   требуют `hasLegalMove()`; null-move — `histPly < MAX_HIST-1`, успешный
   `makeNullMove()` и `hasLegalMove()` после возврата.
9. IIR: при `depth >= 5` и отсутствии TT-хода уменьшить глубину на 1.
10. Генерация и сортировка ходов.
11. Pre-move pruning: futility, LMP, SEE pruning.
12. PVS: первый ход — полное окно, остальные — нулевое окно; при улучшении —
    re-search; LMR для тихих ходов.
13. Обновление killers/history, capture history и countermove при beta-cutoff.
14. Запись в TT с depth/aging-заменой.

### Quiescence

- В шахе: генерирует все ходы (evasions), не делает stand-pat.
- Вне шаха: stand-pat = `evaluate`; если `>= beta`, возврат; иначе генерирует
  взятия и невзяточные превращения.
- Delta pruning: `standPat + victim + 180 < alpha` → пропуск.
- SEE-отсечение для взятий, кроме первого легального.
- В шахе без легальных ходов возвращает `-MATE + ply`.

### Порядок ходов

`moveOrderScore`:

1. TT-ход — 1 000 000.
2. Взятия/превращения — MVV-LVA: `100000 + 16 * victimValue − attackerValue`
   (для превращения добавляется ценность фигуры превращения). К взятиям добавляется
   `captureHistory_[side][attackerType][to][victimType]` (не больше 8000).
3. Killers — 90 000 / 89 000.
4. Countermove — 80 000: ход, который ранее оказался хорошим ответом на предыдущий
   ход соперника.
5. History — `history_[side][from][to]`.

История хранится как `[2][64][64]`; при quiet beta-cutoff увеличивается на
`depth * depth`, при переполнении очищается. `counterMoves_[side][prevFrom][prevTo]`
обновляется на quiet beta-cutoff при `ply > 0`; `captureHistory_` — на взятии,
с ограничением сверху `1 << 19`. `clearHistory()` очищает и history, и capture
history, и countermove-таблицу.

### Время

`SearchLimits` содержит `wtime`, `btime`, `winc`, `binc`, `movestogo`, `depth`,
`movetime`, `nodes`, `infinite`, `moveOverhead`.

- `movetime`: `reserve = min(overhead, max(1, movetime / 10))`;
  `soft = hard = max(1, movetime - reserve)`.
- Часы: `mtg = movestogo > 0 ? movestogo : 30`;
  `base = time / mtg + (inc / 4) * 3`;
  `soft = clamp(base, 3, time / 2)`;
  `hard = min(max(3, (time / 4) * 3), soft * 4 + 20)`;
  затем из обоих вычитается overhead.
- Мягкий лимит проверяется после завершённой глубины; жёсткий — внутри поиска
  (каждые 1024 узла) и дополнительно после глубины 8 при `elapsed * 2 > hard`.
- Если задан только один из часов (`wtime`/`btime`), для отсутствующего берётся
  1000 мс; время ограничивается 24 часами, инкремент — 1 000 000 мс.

Это простая, предсказуемая схема; она не учитывает стабильность оценки, best move
stability и другие признаки, которые используют топовые движки.

## 10. NNUE-пайплайн

### Сеть

- Вход: 768 (`INPUTS`).
- Скрытый слой: 64 (`HIDDEN`), ReLU.
- Выход: 1.
- Веса: `float W1[768][64]`, `B1[64]`, `W2[64]`, `B2`.
- Инференс: плотный, без аккумулятора и без квантизации; на каждой оценке
  пересчитываются все активные признаки (до 32 строк по 64 веса).

### Данные

Формат: `FEN|score`, по одной позиции на строку.

- `score` — с точки зрения стороны хода.
- Residual-режим: цель = `score − classicalEvaluate(pos)`, clamp ±800 cp.
- Direct-режим: цель = `score`, clamp ±1500 cp.
- Позиции с `|score| >= MATE_IN_MAX` отбрасываются.

`trainer datagen`:

- играет self-play с движком;
- глубина поиска задаётся аргументом (в экспериментах — 6);
- первые 8 полуходов и 8% остальных ходов выбираются случайно из легальных, чтобы
  разнообразить распределение;
- максимум 220 полуходов на партию;
- TT 32 МБ, очищается перед каждой партией;
- пишет позицию до сделанного хода, метка — `lastScore()` поиска.

`trainer train`:

- 90/10 train/validation, случайное перемешивание;
- Adam, batch 64, lr 0.003, множитель 0.97 за эпоху;
- early stop после 8 эпох без улучшения validation MSE;
- сохраняет лучшую эпоху в C++-файл.

`trainer stats` считает RMSE классической оценки относительно цели, correlation,
bias и диапазоны.

### Смешивание

См. раздел 8. `direct` — это флаг в сгенерированном файле весов, а не UCI-опция.
`NNUEWeight` задаёт силу смешивания; `UseNNUE` — глобальный выключатель.

### Почему это экспериментально

- Сеть маленькая и не имеет королевских бакетов.
- Residual-метки — оценки поиска глубины 6, а не результат партии; сеть учится
  повторять смещённую оценку движка.
- Direct-метки — статическая оценка Stockfish, которая сжата по шкале; сеть
  наследует это сжатие и при смешивании может недооценивать материал.
- Нет аккумулятора и SIMD, поэтому инференс заметно замедляет поиск.
- Контролируемых SPRT-матчей, доказывающих прирост, нет. В коротких сериях
  `experiments/nnue/logs` (16–24 партии на `cb_exp.exe`) ни одна конфигурация сети
  не превысила 50%; быстрые матчи с включённой сетью проигрывались классической
  оценке.

## 11. UCI-слой

`UciEngine` хранит `Position`, `TranspositionTable`, `Search` и `std::thread worker_`.

- `uci` печатает `id name ChessBot 2.0 NNUE`, автора и опции.
- `setoption` поддерживает `Hash`, `Move Overhead`, `UseNNUE`, `NNUEWeight`,
  `NNUEClip`, `Clear Hash`.
- `ucinewgame` ставит startpos, очищает TT и историю поиска.
- `position startpos|fen ... [moves ...]` применяет ходы через `parseMove` и
  `makeMove`; нелегальный ход обрывает разбор.
- `go` разбирает параметры, вычисляет лимиты и запускает `Search::run` в отдельном
  потоке.
- `stop`/`quit` останавливают и джойнят поток.
- `d`, `eval`, `perft`, `bench` — отладочные команды; `perft` ограничен глубиной
  0…15, `d`/`eval` останавливают текущий поиск.
- `ponderhit` игнорируется; `go ponder` не включает реальный pondering.

Важные детали текущей реализации:

- Конструктор `UciEngine` вызывает `pos_.setStartpos()`, поэтому после запуска
  позиция уже начальная; `ucinewgame` делает то же самое. Присылать `position`
  перед первым `go` не обязательно, хотя GUI обычно это делает.
- `position fen` при ошибке разбора сбрасывает позицию в startpos и печатает
  `info string invalid FEN, using startpos`. Сам `Position::setFen` при ошибке
  возвращает `false` и оставляет очищенную позицию, поэтому вызывающий код обязан
  проверить результат.
- `go` дополнительно проверяет `kingSq[WHITE]`/`kingSq[BLACK]`: если королей нет,
  позиция сбрасывается в startpos. Это защита от пустой/невалидной позиции.
- `setoption` использует `safeInt` с fallback; часы FEN парсятся через `try/catch`.
  Нечисловые значения больше не приводят к необработанному `std::invalid_argument`.
- `d` печатает `pos_.ascii()` и делает `std::flush`, поэтому вывод виден сразу.
- `Position::inCheck()` проверяет `kingSq >= 0`, `isSquareAttacked()` — `validSq`,
  `makeMove()` — переполнение истории; null-move в поиске также проверяет
  `histPly`. Эти защиты добавлены после QA-прогона, который описан в
  `tests/REPORT.md`; исторические 7 провалов относятся к сборке до фиксов.
- Для `go movetime` резервируется примерно 10% бюджета: `movetime 1000` даёт
  около 900 мс поиска, а не 70%. Для часов сохраняется полный `Move Overhead`.

`bench` использует шесть фиксированных FEN из `uci.cpp` (startpos, Kiwipete и четыре
позиции на тактику/эндшпиль), depth по умолчанию 10. TT не пересоздаётся —
используется текущая TT (по умолчанию 64 МБ). Это означает, что `bench` зависит от
состояния TT; для чистых замеров запускайте его в свежем процессе или после
`ucinewgame`.

## 12. Сборка и артефакты

`build.ps1`:

```text
g++ -std=c++20 -O3 -march=native -flto -DNDEBUG -Wall -Wextra -pthread
    -o chessbot.exe src/uci.cpp <ENGINE_SOURCES>
    -flto -static-libgcc -static-libstdc++ -Wl,--stack,33554432
```

`ENGINE_SOURCES` = `bitboards.cpp`, `position.cpp`, `eval.cpp`, `search.cpp`,
`nnue_weights.cpp`.

Почему 32 МБ стека:

- `Position` содержит `keyHist[4096]` и `undoStack[4096]` — это около 160 КБ;
- `Search` содержит `history_[2][64][64]`, `captureHistory_`, `pvTable_[128][128]`,
  `killers_`, `evalStack_`, `rootMoves_[256]` — ещё сотни килобайт;
- рекурсия `negamax`/`quiescence` идёт до `MAX_PLY = 128`;
- на Windows стандартный стек 1 МБ, поэтому без увеличения возможны падения.

`CMakeLists.txt` использует те же оптимизационные флаги (`-O3 -march=native -flto
-Wall -Wextra`) и 32-МБ стек; pthread подключается через `Threads::Threads`. Ветка
`if(MSVC)` добавляет `/STACK:33554432`, но не тестировалась. Исходники теперь
используют стандартные `std::popcount`/`std::countr_zero` из `<bit>`, поэтому порт
под MSVC теоретически возможен, но требует отдельной проверки.

`src/nnue_weights.cpp` — сгенерированный файл примерно на 680 КБ; он увеличивает
время компиляции/линковки. Для сборки без сети можно заменить его на
`src/nnue_weights_placeholder.cpp` (в текущие списки сборки он не входит).

## 14. Инварианты и точки расширения

### Инварианты

- После `setFen`/`setStartpos` в позиции ровно один белый и один чёрный король.
- `makeMove` вызывается только для ходов, сгенерированных из текущей позиции; иначе
  поведение не определено.
- `histPly` не должен превышать `MAX_HIST`; при приближении к пределу `makeMove`
  возвращает `false`, не выполняя ход.
- `TTEntry` обязан оставаться 16 байт (`static_assert`).
- `Move` использует 19 бит; при добавлении новых типов нужно проверить маски.
- Поиск не потокобезопасен: один экземпляр `Search`/`Position`/TT на процесс.
- `stopFlag` — атомарный; проверяется в узлах и между глубинами.

### Куда добавлять

| Задача | Точка входа |
|---|---|
| Новая оценка | `classicalEvaluate` или отдельный термин в `eval.cpp` |
| Новый признак NNUE | `NNUE::featureIndices` + размерности в `engine.hpp` + тренер |
| Новая эвристика поиска | `negamax` до/после генерации ходов |
| Новый порядок ходов | `moveOrderScore` |
| Syzygy | `src/syzygy.cpp`: `probeWDL` в `negamax`, `probeRoot` в `Search::run`; root — только main thread |
| SMP | отдельный пул потоков, потокобезопасный TT, разделяемая история/stop |
| MultiPV | `searchRoot` должен возвращать несколько корневых линий, UCI — `multipv` |
| Новая UCI-опция | `uci()` и `setOption` |
| Новый формат весов | `writeWeights` и загрузка/инициализация в `NNUE` |

## 15. Что намеренно отсутствует

- Syzygy/Гавраше tablebases: локальные WDL/DTZ сделаны; DTM и онлайн-проб нет.
- Многопоточный поиск есть (Lazy SMP); pondering и MultiPV — только в отдельной
  analysis-сборке.
- Chess960, `searchmoves`.
- Opening book и online-базы.
- Полноценный FIDE-анализ мёртвых позиций.
- Сложные техники top-движков: singular extensions, continuation history,
  correction history, NNUE accumulator, SIMD-инференс, кластерный TT,
  dynamic time management.
- CI, unit-тесты и воспроизводимый набор матчей против внешних движков с PGN.

Эти ограничения — осознанный выбор в пользу компактности и понятности. Они же
объясняют разрыв в силе с полноценным Stockfish.

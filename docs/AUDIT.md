## Найденные проблемы

### P0. Несколько экземпляров lichess-bot → 429 и time forfeit

Симптом: несколько запусков `bot2..bot7` одновременно/подряд; Lichess начал
отдавать `429 Too Many Requests` на `/api/stream/event`, event stream перестал
присылать события, бот перезапускался, игровой воркер убивался, а часы шли.
Первая партия `z8rVE1jN` закончилась **time forfeit** (−311).

Что сделано:
- оставлен **один** экземпляр;
- `start_bot.cmd` теперь проверяет уже запущенный
  `lichess-bot.py` и не стартует второй;
- в локальном `lichess-bot` увеличен watchdog event stream и добавлен sleep
  на `RateLimitedError`, чтобы не долбить 429 каждую секунду.

Остаточный риск: при убийстве процесса во время партии партия всё равно
проигрывается по времени. Не останавливайте бота во время игры.

### P1. Helper-поток может остановить всю группу по своему таймеру

`src/search.cpp:127`:

```cpp
if (timeLimited_ && elapsedMs() >= hardLimitMs_) {
    stop();
    return true;
}
```

Это выполняется и для helpers. Helper стартует чуть раньше main, поэтому его
hard deadline может наступить раньше; `stop()` поднимает общий `shared_->stop`,
и main завершается досрочно. На практике это единицы-десятки миллисекунд, но
на bullet это может стоить глубины.

Исправление: проверять время только в главном потоке:

```cpp
if (mainThread_ && timeLimited_ && elapsedMs() >= hardLimitMs_) { ... }
```

Helpers и так завершатся по общему `stopped()`.

### P1. Syzygy включён, но полный набор только 3–4 фигуры

`config.yml`:

```yaml
SyzygyPath: data/syzygy
```

`data/syzygy` содержит только 3–4-piece WDL/DTZ. `SyzygyProbeLimit` не задан,
поэтому effective limit = `TB_LARGEST` = 4. В эндшпилях 5–7 фигур движок
играет обычным поиском.

Рекомендация: скачать полный 3-4-5 WDL+DTZ (Syzygy, ~1.3 ГБ) и выставить
`SyzygyProbeLimit: 5`. 6-piece (160 ГБ) — только если есть быстрый SSD/RAM.

### P2. Лишний вызов TB-probe на каждом узле

`src/search.cpp:329`:

```cpp
if (!rootNode && tbEnabled_ && depth >= tbProbeDepth_) {
    const Syzygy::Wdl wdl = Syzygy::probeWDL(pos_);
```

`probeWDL` сам проверяет число фигур, castling и halfmove, но вызов + atomic
loads происходят на каждом узле. Замер `bench 12` с TB и без: NPS
1.449M vs 1.453M — практически незаметно, но в миттельшпиле при включённом TB
лучше проверять дешёвые условия до вызова:

```cpp
if (tbEnabled_ && depth >= tbProbeDepth_ &&
    std::popcount(pos_.occ) <= tbMaxPieces_ &&
    pos_.castling == 0 && (!tbRule50_ || pos_.halfMove == 0))
```

### P2. `Syzygy50MoveRule=false` не отключает 50-move в самом поиске

Опция влияет только на TB-probe. `Position::isDraw()` всё равно считает
`halfMove >= 100` ничьей до TB-probe. Для обычной игры это корректно; для
анализа с отключённым правилом 50 ходов поведение будет несогласованным.
Это не влияет на Lichess-партии с включённым правилом.

### P2. Event stream watchdog 3600 с — компромисс

После локального патча бот не перезапускается час при пропаже ping, чтобы не
убить текущую партию. Но если поток умер, новые вызовы могут не приходить.
Идеально: перезапускать control stream только когда нет активных партий.

### P2. Двойной резерв времени

В конфиге:

- `move_overhead: 1000` (lichess-bot),
- `Move Overhead: 150` (движок).

Итого ~1.15 с резерва на ход. Для 180+1 это нормально, для 60+1 — заметно
уменьшает время на обдумывание. Не баг, но стоит измерить 500/1000 и 150/50.

### P3. Matchmaking часто отменяет вызовы

Бот с provisional-рейтингом ищет 2250–2750, многие боты отклоняют вызовы.
Это не ошибка движка. Можно расширить `opponent_rating_difference` до 400
или добавить `rating_preference: low`, но только после набора рейтинга.

### P3. Дашборд создаёт дополнительный трафик

`/api/data` каждые 5 с + `/api/moves`/`/board` при живой партии. Это не влияет
на поиск, но добавляет запросы к Lichess. При 429 можно увеличить интервал до
10 с. Токен на сервере, в браузер не попадает.

## Что проверено и не является багом

- QA: **358/358**; perft 54/54; 8-потоковый стресс 120 циклов — 0 ошибок.
- Syzygy root: KQvK/KQvKR/KPvK/EP/promotion совпадают с Lichess tablebase.
- TT: lockless 16-byte slots, busy/checksum/acquire-release; MT fixed-depth
  regression и self-play не выявили нелегальных ходов.
- История партии передаётся python-chess как `position ... moves ...`, поэтому
  repetition/50-move история не теряется.
- Текущие партии: легальные ходы, глубина 18–49, 5–9M NPS; time forfeit был
  только из-за перезапуска процесса, не из-за тайм-менеджмента движка.
